## 7. Findings

### F1 — the ruling carried on a 3/5 margin, with 2 validator `TIMEOUT`

`rule` (row 5) reached the correct outcome but two of five validators timed out
rather than voting. This is the same validator-side divergence under node load
already recorded for cases 001-v2 and 003-v2. It is not a contract fault, and
the outcome is correct, but a 3/5 margin is thinner than the 5/5 that every
other transaction in this run achieved.

### F2 — a duplicate `release()` was submitted and correctly refused

**What happened.** Twenty-seven seconds after the customer created the release
(row 6, `txSlot` 5), the provider created a second one from a browser tab showing
`RULED` (row 7, `txSlot` 6). Bradbury queued it in the next slot behind the
first. By the time it executed, the agreement was `RESOLVED`, so the contract's
single-shot guard refused it: **5/5 DISAGREE, `FINISHED_WITH_ERROR`, no state
change, no additional funds moved.** The settlement recorded on-chain is the
first release, unchanged, and the contract balance is zero.

**This is the negative test the design predicts**, and it is the same guard
already exercised on case 002-v2. It cost the provider gas and half an hour of
waiting; it could not have cost the escrow.

**What the frontend fix does and does not close.** The frontend was hardened in
commit `0505189`: availability is now re-derived from a
fresh read before the confirmation dialog opens *and* again immediately before
the write is submitted, a status seen by another tab withdraws the action at
once, and postconditions are bound to the transaction hash and method that
produced them.

Stated plainly, that would **not** have blocked this particular submission:

- At 16:27:51 the contract's readable state was still `RULED`. The customer's
  release had been created 27 seconds earlier and was neither accepted nor
  finalized, and **an unfinalized transaction by the counterparty is not visible
  in contract state**. A pre-submit re-read would have seen `RULED`, found
  `release` available, and correctly allowed it.
- The cross-tab guard shares state through one browser profile's local registry.
  The two parties were different wallets in different profiles, so nothing was
  shared to compare.

What `0505189` does close is the case where the state **has already moved** — a
tab still offering Release minutes or hours after the agreement resolved — and
it makes this outcome legible: the duplicate is now reported under its own
transaction as *safely rejected: no state changed and no funds moved*, instead of
a bare execution failure sitting beneath a postcondition belonging to an earlier
action.

**The residual race is not closable from the client.** Two parties may always
submit competing writes inside one finality window; only the contract can
arbitrate that, and it does. This is a limitation of any UI over a chain with
~30-minute finality, and it is why the single-shot guard exists.

```bash

node deploy/scripts/gl.mjs history --contract 0x5006115944D7F593E401239aeDb64abEF13dCc0a

node deploy/scripts/gl.mjs read --contract 0x5006115944D7F593E401239aeDb64abEF13dCc0a --method get_settlement_status
```

The method names in section 4 come from each transaction's `txCalldata`, which
encodes a map whose `method` key holds the name as a typed string — low 3 bits of
the value's varint are the type (4 = str), the rest is the byte length. The
explorer index does not carry the method, and the SDK's `decodeInputData`
returns an empty `callData` for these calls, so the name was decoded from the
raw blob rather than assumed from ordering.
